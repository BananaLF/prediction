# 员工模式全局 Skill 设计

## 状态

设计已获用户确认，待审查本文档后编写实施计划。

## 背景

希望在任意 Codex 会话中按需启用一种“员工模式”：接收 GitHub Issue 后，严格经过需求理解、设计审查、实施审查和合并审查，完成代码、测试、Pull Request、合并以及 Issue 和 worktree 清理。

该模式需要同时满足两个看似相反的要求：

- 普通 Codex 会话不应被自动套用 Issue 工作流。
- 启用后，流程必须可重复、可检查，并且不能因为上下文中的模糊表述而越过人工审批。

因此，本方案使用可手动加载的全局 Skill，而不是常驻 agent 或全局 `AGENTS.md`。Skill 负责提供流程规则；当前 Codex 会话负责实际执行，不引入后台进程或独立状态服务。

## 目标

1. 在任意 Codex 会话中通过显式调用 `$employee-mode` 启用员工模式。
2. 启用后能够从 Issue 开始，在独立 worktree 中完成设计、计划、实施、PR 和合并流程。
3. 在设计、实施和合并三个阶段分别要求精确的人工审批口令：`批准设计`、`批准实施`、`批准合并`。
4. 合并前检查 `main` 是否有新提交；若有，先将最新 `main` 合并到 PR 分支，再重新测试和审查。
5. 将对 Issue 目标和 `main` 分支的影响以可审查的报告形式写入 Issue 和 PR，然后再等待合并批准。
6. PR 成功合并后删除本次 worktree，并关闭对应 Issue。
7. 在任何异常或权限不足时停止在安全边界内，报告阻塞原因，不自动绕过审批或强制覆盖变更。

## 非目标

- 不创建常驻、自动轮询 Issue 的后台 agent。
- 不通过全局 `AGENTS.md` 强制所有会话进入员工模式。
- 不把 GitHub 的 Review “Approve”、`LGTM`、标签或 Issue 状态当作本 Skill 的审批口令。
- 不在用户未启用 `$employee-mode` 时自动执行该工作流。
- 不自动解决合并冲突、不使用 force push、不删除用户未授权的 worktree 或分支。
- 不规定项目业务代码的实现方式；实现方案仍由 Issue、设计文档和实施计划决定。
- 不在本次 Skill 中引入额外的持久化数据库、守护进程或第三方服务。

## 方案选择

### 方案 A：全局指令型 Skill（采用）

创建 `~/.agents/skills/employee-mode/SKILL.md`，通过用户显式调用 `$employee-mode` 激活。Skill 文件包含工作流、状态门禁、Git/GitHub 操作规则和失败处理规则。

优点：

- 可在任意仓库和会话中复用。
- 默认不影响普通会话。
- 不需要维护常驻进程或自定义 agent 生命周期。
- 审批状态可以直接由当前会话和 Issue/PR 评论共同呈现，容易人工检查。

限制：

- Skill 本身不能在会话结束后后台继续工作。
- 用户需要在新的会话中再次显式调用 Skill，并提供当前 Issue 或恢复上下文。

### 方案 B：Custom Agent

可以封装一个名为“员工 agent”的独立角色，但它更适合固定人格、工具权限和长期角色配置。当前需求的核心是“可选工作流”，而非需要独立运行时或并行生命周期，因此会增加配置和调用复杂度。

### 方案 C：全局 `AGENTS.md`

全局指令能够自动影响会话，但无法满足“有时不一定需要”的要求，会把 Issue 工作流意外带入普通任务，故不采用。

## 总体设计

### 1. Skill 位置与激活

Skill 的目标位置为：

```text
~/.agents/skills/employee-mode/SKILL.md
```

建议元数据：

```yaml
---
name: employee-mode
description: 在用户显式调用 $employee-mode 后，按严格人工审批门禁处理 GitHub Issue，并在独立 worktree 中完成设计、实施、PR、合并和清理。
---
```

激活条件是用户明确调用 `$employee-mode`，或明确要求启用“员工模式”。仅有“处理这个 Issue”“帮我修复”之类的普通请求，不足以自动激活该 Skill。

激活后，Skill 首先要求用户提供 Issue 编号或 URL，并确认当前仓库是任务范围。若 Issue、仓库、基线分支或必要的 GitHub 权限无法确定，应先询问或检查，不创建 worktree。

### 2. 会话内状态机

工作流使用明确的阶段状态。阶段状态以当前会话为主，并通过提交、Issue 评论和 PR 信息留下可恢复的外部记录：

```text
待接收 Issue
  -> 已创建 worktree
  -> 设计待审批
  -> 实施计划待审批
  -> 实施中
  -> PR 待合并前审查
  -> 合并待审批
  -> 已合并并清理
```

每次响应开始前，Skill 都要识别当前阶段，并只执行该阶段允许的动作。用户在错误阶段发送审批口令时，不得将其解释为其他阶段的授权；应说明当前阶段和期望口令。

如果会话中断，恢复时先从 Issue 评论、PR 状态、分支提交和 worktree 状态重建阶段，无法确定时暂停并请求用户确认，不猜测已经完成的审批。

### 3. Issue 与分支隔离

收到 Issue 后执行以下准备检查：

1. 确认当前目录是目标 Git 仓库，并读取 Issue 标题、正文、评论、标签和状态。
2. 获取远程信息，并从最新 `origin/main` 创建任务分支。
3. 使用仓库约定的 `.worktrees/` 目录创建独立 worktree；分支名称采用稳定、可读且经过安全清理的 Issue 标识，例如 `employee/issue-<number>-<slug>`。
4. 检查目标 worktree 和分支是否已经存在。若存在且无法明确属于当前任务，停止并报告，不覆盖。
5. 后续代码、测试、设计文档和计划均在该 worktree 中完成；主工作目录只作为协调入口，不直接承载 Issue 实施改动。

创建 worktree 失败、`main` 无法同步、Issue 已关闭且用户未要求重新打开，或 GitHub 权限不足时，停在准备阶段。

### 4. 设计阶段

在 worktree 中读取 Issue 和相关代码后，使用 `superpowers:brainstorming` 深入确认：

- Issue 的真实目标、范围、成功标准和非目标。
- 受影响的组件、数据流、接口、配置和兼容性。
- 备选实现方案、取舍、风险和测试策略。
- 是否需要补充 Issue 信息才能安全实施。

形成设计文档并提交到任务分支，建议路径为：

```text
docs/superpowers/specs/YYYY-MM-DD-<issue-slug>-design.md
```

然后在 Issue 中发布设计文档链接、设计摘要、测试计划和待确认风险。此时只允许等待设计审批，不得开始编写业务实现或实施计划。

只有用户单独发送精确文本 `批准设计` 后，才能进入实施计划阶段。以下表达均不视为批准：`没问题`、`可以`、`继续`、`LGTM`、GitHub Review Approve 或标签变化。

### 5. 实施计划阶段

收到 `批准设计` 后，基于已批准的设计文档编写可执行的实施计划，建议路径为：

```text
docs/superpowers/plans/YYYY-MM-DD-<issue-slug>-implementation.md
```

计划应包含文件级改动范围、接口/数据结构变化、逐步实施顺序、测试先后关系、失败处理、验证命令和提交边界。计划完成后提交到任务分支，并把链接和摘要更新到 Issue。

随后暂停，等待精确文本 `批准实施`。在此之前不修改业务代码、不运行会改变外部状态的 GitHub 操作，也不创建 PR。

### 6. 实施与 PR 阶段

收到 `批准实施` 后，按计划在任务 worktree 中实现：

1. 按项目约定使用相关开发技能，例如 worktree、TDD、系统调试和完成前验证。
2. 先建立或更新窄范围测试，再实施最小必要代码改动。
3. 运行与风险匹配的测试、静态检查和格式检查；失败时停止修复循环并报告证据，不能声称完成。
4. 提交实现和测试，推送任务分支，创建 Pull Request 指向 `main`。
5. 如果 PR 默认是 Draft，实施阶段仍可保持 Draft；在合并前阶段才执行 Ready for review 转换。
6. 在 Issue 中更新实现摘要、验证结果和 PR 链接。

创建 PR 后进入审查等待状态，不因某个 GitHub Review 或评论自动进入合并流程。用户若提出修改意见，应在当前 PR 分支处理并重新验证；若修改影响设计或计划，应回到相应审批阶段重新获得明确批准。

### 7. 合并前主分支同步与影响审查

在用户发送 `批准合并` 之前，必须完成一次最终合并前检查。该检查也是合并批准的前置条件：

1. `git fetch origin main`，比较 PR 分支基于的 `main` 与最新 `origin/main`。
2. 若 `main` 没有新提交，继续最终验证。
3. 若 `main` 有新提交，在 PR 分支上执行普通 merge，将最新 `origin/main` 合并进任务分支；不得 rebase、force push 或覆盖他人提交。
4. 若出现冲突，保留现场并停止，列出冲突文件和需要人工决策的内容。
5. 同步成功后重新运行相关测试和检查，并推送更新后的 PR 分支。
6. 审查最终差异是否仍满足 Issue 目标，并检查新 `main` 改动是否影响：API/接口、数据模型与迁移、配置、运行时行为、回归风险、性能、安全性和测试覆盖。
7. 将审查结果写成报告，至少区分“无影响”和“发现影响”；每项影响包含文件/行号、证据、对 Issue 目标的影响和建议动作。
8. 将同一报告链接或摘要更新到 Issue 和 PR，明确说明测试命令、当前基线提交和 PR 状态。

只有完成以上检查并报告后，才进入“合并待审批”。如果主分支在批准后、实际合并前再次变化，原批准失效；必须重复同步、测试和影响审查，再次等待 `批准合并`。

### 8. PR 状态与合并

收到精确文本 `批准合并` 后，先再次执行主分支最新检查，并确认：

- PR 分支包含最新 `main`，且同步后的验证已通过。
- PR 不是 Draft。若是 Draft，使用 `gh pr ready <PR>` 将其转换为 Ready for review，并重新确认 CI、Review 和分支保护状态。
- 必需 CI、必需 Review、分支保护和合并权限均满足仓库规则。
- PR 没有未解决冲突，目标分支仍为 `main`。

上述任一条件不满足时不合并，报告具体阻塞原因。条件满足后使用 GitHub CLI 的 PR merge 操作合并，采用仓库允许且与 PR 当前策略一致的合并方式；不强制绕过分支保护。

### 9. 收尾与清理

仅在确认 PR 已成功合并后：

1. 记录 merge commit、PR URL 和 Issue URL。
2. 删除本次本地 worktree，并确认删除目标只对应当前任务。
3. 删除任务远程分支仅在仓库策略和用户授权允许时执行；否则保留并说明。
4. 关闭 Issue，并在 Issue 中补充最终摘要、PR、merge commit、验证结果和清理结果。
5. 向用户报告完成状态，回到等待下一个 Issue 的空闲状态；下一个任务仍需显式激活或继续当前员工模式会话。

如果合并成功但 worktree 清理或关闭 Issue 失败，不能回滚已完成的合并；应保留现场并报告剩余手工步骤。

## 审批门禁契约

| 阶段 | 进入条件 | 允许动作 | 唯一继续口令 |
| --- | --- | --- | --- |
| 设计待审批 | 设计文档已提交，Issue 已更新 | 阅读、解释、按反馈修改设计 | `批准设计` |
| 实施计划待审批 | 设计获批，计划已提交，Issue 已更新 | 阅读、解释、按反馈修改计划 | `批准实施` |
| 合并待审批 | PR 已创建，主分支已同步，测试和影响报告已发布 | 阅读报告、按反馈修改并重新验证 | `批准合并` |

审批口令必须是用户消息中独立、明确的文字。包含口令但同时表示反对、附加条件或要求修改时，不得继续执行，应先处理条件或重新等待口令。

## 错误与安全边界

- Issue 无法读取：报告 URL/编号、权限或 API 错误，停在准备阶段。
- worktree/分支已存在：不覆盖、不删除，要求用户选择恢复、改名或清理。
- 设计或计划与 Issue 不一致：暂停并回退到对应审批阶段。
- 测试或检查失败：报告命令、退出码和关键输出，修复后重新验证。
- Git merge 冲突：不自动猜解，报告冲突文件和上下文。
- PR 为 Draft、CI 未通过、Review 不足或分支保护阻塞：不调用 merge，报告阻塞条件。
- GitHub CLI、远程网络或权限不可用：可以完成本地只读检查，但不伪称已推送、已创建 PR 或已合并。
- 清理操作目标不明确：不执行删除，保留 worktree 并请求确认。

所有外部写操作（Issue 评论、推送、创建 PR、Ready for review、合并、关闭 Issue、删除远程分支）都必须对应当前工作流阶段，且在达到相应审批门禁后执行。

## 验证与验收标准

Skill 实现完成后至少验证：

- 未显式调用 `$employee-mode` 的普通会话不会进入员工流程。
- 显式调用后能识别 Issue、创建隔离 worktree，并从最新 `origin/main` 建立任务分支。
- 设计、计划、实现、PR、合并和收尾顺序不可跳过。
- `批准设计`、`批准实施`、`批准合并` 之外的表述不能推进阶段。
- 主分支发生变化时能 merge 最新 `main`、重新测试和重新审查；冲突会停止。
- 合并前影响报告同时出现在 Issue 和 PR，并包含可定位证据。
- Draft PR 会先转换为 Ready for review，再检查 CI/Review/分支保护后合并。
- 合并成功后 worktree 清理和 Issue 关闭按顺序执行；清理失败不会伪称全部完成。
- Skill 文档本身无自相矛盾的触发条件、审批规则和外部写操作权限描述。

## 实施范围

实际实现阶段只创建和验证全局 Skill 文件，并根据需要提供最小的示例/验证文档；不修改本仓库业务代码，不新增常驻服务，不改变项目已有 GitHub 分支保护或合并策略。
