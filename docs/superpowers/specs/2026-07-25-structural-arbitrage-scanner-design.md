# Polymarket 结构套利扫描器设计

日期：2026-07-25
状态：已由用户逐段批准
阶段：三个盈利能力周期中的第一周期

## 1. 目标

构建一个 Python 事件驱动、模块化的只读系统，检测并仿真 Polymarket 内部结构套利。
系统同时提供单次扫描和持续监听，以真实订单簿深度、市场实时费率、最小订单量、精度和
跨腿执行风险计算机会。

第一阶段模拟本金为 1,000 美元。只有在扣除手续费、价格冲击和 0.25% 安全缓冲后，
净收益率仍不低于 0.75% 的组合才报警。不另设最低绝对利润。

本阶段不读取私钥、不调用认证交易接口、不提交真实订单。验收不要求市场必须出现机会。

## 2. 范围

### 2.1 包含

- 二元 YES/NO 完整集合；
- 同一事件的多结果、互斥且完备集合；
- 人工审核的蕴含、互斥和等价市场关系；
- `scan-once` REST 快照扫描；
- `watch` WebSocket 持续监听；
- SQLite 审计、离线重放、终端报警和 macOS 桌面通知；
- 为未来 Kalshi 数据适配器预留标准化接口，但不实现 Kalshi 集成。

### 2.2 不包含

- 概率预测模型；
- 做市或奖励优化；
- 自动语义关系直接进入生产；
- 裸卖空或假定已有头寸；
- 密钥管理、认证、下单、撤单或真实资金；
- Web 控制台、云部署或多节点服务。

## 3. 设计原则

- 宁可漏报，不可用不一致或不完整数据误报。
- 使用可成交 ask 和完整深度，不使用页面概率、中间价或最后成交价代替。
- 所有货币、价格和数量运算使用 `Decimal`，禁止二进制浮点参与财务判定。
- 自动发现只产生待审核关系；只有有效的人工规则可触发报警。
- 每条报警必须包含足够证据，能够在无网络条件下确定性重放。
- 第一版优先正确性和可审计性；测得瓶颈后才考虑拆服务或更换语言。

## 4. 架构

系统为单进程模块化应用，各组件通过显式数据结构通信。

### 4.1 `MarketCatalog`

使用 Gamma API 的 keyset/游标分页同步活跃事件、市场和 outcome token，保存：

- event、market、condition 和 token 标识；
- outcome、结算时间和市场状态；
- CLOB 可用性、`negRisk`、tick size 和费用状态；
- 原始结算规则与来源。

关闭或结算的市场只更新状态，不删除历史记录。

### 4.2 `OrderBookGateway`

- `scan-once` 通过批量 `POST /books` 获取完整订单簿；
- `watch` 通过公开 market WebSocket 订阅 `book`、`price_change`、
  `tick_size_change` 和市场生命周期事件；
- WebSocket 建立前先通过 REST 获取基准快照；
- 每 30 秒抽样 REST 校验本地订单簿；
- 断线、哈希异常、时间倒退或未知消息结构会使受影响订单簿失效；
- 恢复时必须重新获取完整快照，不允许从旧状态继续应用增量。

### 4.3 `RelationRegistry`

关系集合定义：

- 所有可能且互斥的世界状态；
- 每个 token 在各状态下的 0/1 结算收益；
- 哪些状态被规则允许；
- 规则依据、人工审核信息、版本和有效期。

系统可生成待审核候选，但只有状态为 `active` 且校验通过的规则可供套利引擎使用。

### 4.4 `ExecutionSimulator`

给定关系集合和一致性订单簿：

- 按价格优先逐档消耗 ask；
- 所有组合腿使用同一份数；
- 应用每个 token 的实时费率；
- 应用 tick size、数量精度和最小订单量；
- 应用 0.25% 安全缓冲；
- 限制总投入不超过 1,000 美元；
- 计算最大可成交数量、最大净利润数量和最大净收益率数量；
- 计算最坏单腿失败损失和建议下单顺序。

### 4.5 `ArbitrageEngine`

引擎使用统一的状态收益向量，不为不同套利类型维护互相独立的启发式公式。
它只寻找“买入 token”的组合，使组合在每个有效世界状态中的结算收益不低于统一保证值。

二元完整集合、多结果完整集合和人工逻辑关系都转换为同一问题。

### 4.6 `OpportunityStore`

SQLite 使用 WAL 模式，至少包含：

- `events`
- `markets`
- `tokens`
- `relation_sets`
- `relation_states`
- `relation_payoffs`
- `orderbook_snapshots`
- `orderbook_levels`
- `opportunities`
- `opportunity_legs`
- `runs`
- `notifications`

机会记录包含关系版本、引擎版本、费率、完整订单簿深度、交易腿、时间戳、成本拆分、
保证收益、净利润、净收益率和最坏单腿失败损失。

### 4.7 `Notifier`

- 终端输出高亮的人类可读摘要；
- `scan-once` 同时支持机器可读 JSON；
- macOS 桌面通知失败只写日志，不得中断扫描；
- 相同关系、交易腿、订单簿哈希和经济结果的机会去重；
- 只有收益率、可成交数量或订单簿哈希发生实质变化时才重复通知。

## 5. 套利数学

设有效世界状态集合为 \(S\)，买入 token 集合为 \(T\)，每个 token 的份数为 \(q\)。
token \(t\) 在状态 \(s\) 下的结算收益为 \(P_{t,s}\in\{0,1\}\)。

保证结算收入为：

\[
G(q) = \min_{s \in S}\sum_{t \in T} qP_{t,s}
\]

对每条腿逐档消耗订单簿得到买入成本 \(C(q)\)，逐腿费用为 \(F(q)\)，安全缓冲为：

\[
B(q) = 0.0025 \times C(q)
\]

则：

\[
I(q)=C(q)+F(q)+B(q)
\]

\[
\text{Profit}(q)=G(q)-I(q)
\]

\[
\text{Return}(q)=\frac{\text{Profit}(q)}{I(q)}
\]

候选数量来自订单簿深度发生变化的位置，并经过最小订单量、精度和 1,000 美元资金上限裁剪。
只有 `Return(q) >= 0.0075` 才可能报警。

## 6. 有效机会条件

报警必须同时满足：

- 净收益率不低于 0.75%；
- 所有腿在同一快照窗口内可完整成交；
- 总投入不超过 1,000 美元；
- 每腿满足最小订单量、tick size 和数量精度；
- 市场可交易且未暂停、关闭或结算；
- 订单簿数据年龄不超过 1 秒；
- 各腿交易所时间戳偏差不超过 250 毫秒；
- 关系规则状态为 `active` 且版本有效；
- 费用参数完整；
- 所有经济判断均基于 ask 深度。

多腿订单并非跨腿原子成交。因此产品用语固定为“快照可执行机会”，不得称为无执行风险套利。

## 7. 数据流

### 7.1 `sync-markets`

1. 分页读取活跃市场。
2. 标准化并写入市场、token 和费用元数据。
3. 更新已存在市场的生命周期状态。
4. 为结构明确的事件生成待审核完整集合候选。
5. 为可能的逻辑关系生成研究候选，但不自动启用。

### 7.2 `scan-once`

1. 读取所有有效关系及涉及 token。
2. 分批获取订单簿和费用参数。
3. 为每批分配捕获时间和扫描批次 ID。
4. 运行仿真和套利判定。
5. 保存有效机会及接近门槛的诊断。
6. 输出 JSON 和摘要，并在需要时发送桌面通知。

### 7.3 `watch`

1. 用 REST 建立基准订单簿。
2. 订阅相关 token。
3. 每次增量只重新计算受影响关系。
4. 定期校验本地订单簿。
5. 失效时停止相关计算并重建。
6. 保存机会、运行指标和通知结果。

## 8. CLI

```text
predmarket sync-markets
predmarket scan-once
predmarket watch
predmarket relations list
predmarket relations validate
predmarket relations import <yaml-path>
predmarket replay <opportunity-id>
predmarket report
```

规则导入是原子的。系统检查状态完备性、互斥性、token 存在性、收益向量维度、
审核字段和版本；任一错误都会拒绝整个文件。

`replay` 不访问网络，必须从保存的关系版本、费率和完整订单簿得到与原机会相同的结果。

## 9. 故障处理

以下情况使受影响关系进入 `data_invalid`，不运行套利判定：

- WebSocket 断线或收到未知消息；
- 时间戳倒退、跨腿时间偏差超限或数据过期；
- REST 与本地订单簿哈希不一致；
- 缺少任一交易腿、费用或最小订单量；
- 市场状态、tick size 或结算规则发生变化；
- `Decimal` 转换、精度或舍入失败；
- SQLite 事务失败；
- 检测到明显系统时钟跳变。

网络重连使用带随机抖动的指数退避。重连成功不代表数据有效，必须完成 REST 全量重建。
SQLite 写入机会和证据包使用单一事务，防止出现无法重放的半条记录。

## 10. 测试策略

实现严格遵循 RED–GREEN–REFACTOR：先写失败测试并观察失败，再写最小实现，通过后重构。

### 10.1 单元测试

- 逐档成交和数量断点；
- 动态费用、安全缓冲和资金上限；
- 状态收益向量与最坏状态；
- 精度、最小订单量和时间窗口；
- 去重和通知旁路。

### 10.2 性质测试

- ask 上升不能提高利润；
- 深度减少不能提高最大成交量；
- 费用增加不能创造机会；
- 任一有效状态收益不足时不得报警。

### 10.3 契约和集成测试

- 使用冻结的官方 REST/WebSocket 样例；
- 未知结构必须显式失败；
- 本地假服务器模拟快照、增量、乱序、断线、重连和限流；
- 测试不依赖生产网络。

### 10.4 回放测试

- 机会可离线确定性重算；
- 数据库迁移前后的历史机会仍可重放；
- 引擎版本变化时保留原版本输出，不静默覆盖。

## 11. 验收

- 固定样例和历史回放计算全部通过；
- 连续运行 24 小时无崩溃；
- 断线后可自动重建；
- 每条报警保存完整订单簿和计算明细；
- 实时观察至少 7 天；
- 有效机会满足净收益率不低于 0.75%；
- 系统报告运行时间、数据缺口、重连次数、陈旧订单簿数、扫描关系数、
  接近门槛数、有效机会数、理论净利润和最坏单腿失败风险。

七天内未发现机会是合格的测量结果，不允许降低门槛或制造信号来满足数量指标。
